Codex 질문 도구: `request_user_input`은 제공되는 모드에서만 사용한다. 사용할 수 없으면 `request_user_input_async` 또는 간결한 평문 질문을 사용한다. 승인 요청은 현재 세션의 상위 지침을 따르고, 응답이 없다는 이유로 승인 처리하지 않는다.
# issue 단계별 절차 — 앞 절반 (start · grill · plan · implement)

`<P>` = 설치된 플러그인 루트. 스크립트는 `node "<P>/scripts/<이름>.mjs"` 이고 `--json` 이면 마지막 줄이 JSON 한 덩어리다 — 그것만 읽으면 된다.
`<runtime>` = `harness.json.runtime_dir`(기본 `.codex/runtime` — 작업트리에서 실행해도 메인 저장소 것을 쓴다), `<slug>` = 브랜치 이름의 `/` 를 `-` 로 바꾼 것, 상태 JSON = `<runtime>/issues/<slug>.json`.
Codex 에는 Workflow 툴이 없고 이 배포본에는 `workflows/` 가 들어 있지 않다 — 아래에서 다른 에이전트에게 맡기는 일(계획 반증 · 병렬 구현 레인)은 `spawn_agent` 로 띄운다. 역할을 개별 위임할 때는 `subagents/<name>.toml` 의 `developer_instructions` 를 읽어 프롬프트에 넣는다. 에이전트에게 주는 경로는 절대 경로로 쓴다 — 상대 경로는 엉뚱한 트리를 가리킨다.
뒤 절반(verify · gate · commit·push · complete · main 배치)은 [stages-back.md](stages-back.md).

## start

0. **하위이슈 확장 — 사용자가 준 키가 몇 개든 항상**(사용자가 "이 이슈만"·"하위 빼고" 라고 한 경우만 건너뛴다): 키마다 `getJiraIssue`(Atlassian MCP — `fields` 에 `subtasks` 포함. 본문·댓글도 이 호출이 겸한다)를 불러 응답 배열을 `node "<P>/scripts/issue-subtasks.mjs" --in - --json` 의 stdin 으로 준다. 이미 이슈 브랜치 위인데 상태만 없는 `NO_STATE` 는 확장하지 않고 `--status` 의 `keys` 를 그대로 쓴다.
   - `code`: `RESUME` — 이 키로 진행 중인 브랜치가 있다(Jira 의 하위 구성이 바뀌었어도 출력 `keys` 를 그대로 잇는다) · `EXPANDED` — `keys` = 준 키 + 하위(번호 순) · `NO_SUBTASKS`.
   - 끝난 하위(완료 카테고리 · `jira.done_transition` 상태)·다른 프로젝트 키·`subtasks.match`(harness.json — 하위 summary 정규식. 멀티 레포 이슈에서 이 저장소 몫만 고를 때)에 안 걸린 하위는 빠지고 `children[]` 에 `reason` 과 함께 남는다.
   - `confirm: true`(= `subtasks.match` 가 없다)이면 `children[]` 를 표로 한 번 보이고 이 저장소 몫이 아닌 하위(예: 다른 레포의 `[mobile]`)를 빼게 한다 — 뺄 것은 `keys_arg`·`group_args` 에서 지운다. 무인이면 묻지 않고 전부 포함한다. 같은 확인이 되풀이되면 `subtasks.match` 설정을 안내한다.
   - MCP 가 없거나 실패하면 준 키 그대로 가고 보고에 "하위이슈 미확인(사유)" 를 남긴다.
1. `issue-start.mjs <keys_arg> [--worktree [--base <ref>] | --adopt] [--group <group_args 마다>]… --json` — `--group ABC-10=ABC-11,ABC-12` 는 부모↔하위를 상태 JSON `subtasks` 에 남긴다(새 상태를 만들 때만).
   - 기본 브랜치 위: `branch_template`(기본 `feat/{keys}`) 로 새 브랜치를 만들고 상태 JSON 을 쓴다. 이미 이슈 브랜치 위면 브랜치는 두고 상태만 만든다. 상태가 이미 있으면 `RESUMED` — 아무것도 바꾸지 않는다.
   - 그 밖의 브랜치: `ON_OTHER_BRANCH` 로 멈춘다(엉뚱한 브랜치에 이슈를 붙이는 사고 방지). 그 브랜치를 그대로 쓰려면 `--adopt`, 지금 트리를 건드리지 않으려면 `--worktree`.
   - **`--worktree`** — 지금 트리(브랜치·인덱스·작업 파일)는 그대로 두고 `<메인>/.codex/worktrees/<브랜치 끝 이름>` 에 작업트리와 이슈 브랜치를 판다(기본 브랜치 끝에서. 이미 있으면 그것을 쓴다). `herdr.worktree_copy`·`worktree_init` 준비까지 돌리고 출력 `worktree.path` 를 준다 — **이후 명령의 `--cwd` 와 파일을 고치는 자리가 그 경로다.** 이 트리에서 다른 이슈가 진행 중이거나, 여러 이슈를 나란히 하거나, 프로젝트 지침이 이슈마다 작업트리를 쓰라고 하면 이것으로 시작한다(손으로 `git worktree add` 하면 상태·준비·무시 설정이 빠진다).
     **`issue_worktree: "always"`**(harness.json) — 프로젝트가 이것을 켰으면 플래그 없는 시작도 위와 같이 작업트리를 판다: 기본 브랜치 위에서도 지금 트리의 브랜치를 바꾸지 않고, 그 밖의 브랜치 위에서도 `ON_OTHER_BRANCH` 로 멈추지 않는다. 예외는 둘이다 — 지금 트리가 이미 그 키의 이슈 브랜치면(이름이 템플릿과 달라도) 제자리에서 잇고, `--adopt` 는 지금 브랜치를 채택한다. 그래서 **일하는 자리는 플래그나 설정이 아니라 시작 출력으로 정한다 — `worktree.path` 가 있으면 그 경로, 없으면 지금 트리다.**
     지울 때는 `issue-start.mjs --remove-worktree <KEY | 경로> [--force]` — 안의 링크(준비 단계가 건 `node_modules` 등)를 **먼저 끊고** 지운다. 링크를 따라 들어가 메인 쪽 폴더를 지운 사고가 반복됐기 때문이다. 브랜치와 상태 JSON 은 남고, 커밋 안 된 변경이 있으면 `--force` 없이는 거부한다. `<KEY>` 로 부르면 그 이슈의 Herdr 구현 레인이 남긴 작업트리와 레인 브랜치도 함께 치운다(stages-back.md §complete 7 — 이슈 작업트리의 경로로 불러도 그 브랜치의 레인은 같이 치우고, 레인 작업트리의 경로를 주면 그 하나만 지운다).
2. Atlassian MCP(도구 이름은 ToolSearch 로 찾는다 — `getJiraIssue` / `transitionJiraIssue` / `addCommentToJiraIssue`, 필요하면 `getAccessibleAtlassianResources` 로 cloudId 먼저):
   - 본문·댓글은 0번에서 읽은 원문을 쓴다(전달받은 요약보다 원문이 우선 — 번복·누락이 섞인다). 하위로 새로 들어온 키만 더 읽는다. 파일에 저장하지 않는다.
   - `transitionJiraIssue` 를 `jira.start_transition` 으로, `addCommentToJiraIssue` 에 출력의 `jira.comment` 를 그대로 — **키마다**(부모·하위 전부).
   - MCP 가 없거나 실패하면 코드 진행은 막지 않되 보고에 "Jira 미반영(사유)" 를 남긴다.

## grill

`jira-harness 플러그인의 grilling 스킬` 을 그 자리에서 따른다 — 한 번에 한 질문, 선택지 2~4개와 권장안. 코드·문서로 답할 수 있는 것은 묻지 않고 읽어서 답한다. 범위가 본문만으로 안 잡히면 묻기 전에 코드부터 읽는다(넓으면 탐색 서브에이전트 하나에 "이 요구가 어디에 걸리는가" 만 묻는다 — 결정은 넘기지 않는다).

- 사람이 정한 것: `issue-set.mjs --decision "<질문>" "<답>"`.
- **혼자 고른 해석**(요구의 뜻이 갈리는데 묻지 않고 정한 것 — 무인 모드 · "알아서 해" · 코드에서 읽어 낸 추정): `issue-set.mjs --assume "<갈림길>" "<고른 해석 — 근거>"`. 가정은 계획 승인 요약과 마감 댓글의 맨 위에 올라간다. 다시 열린 이슈의 여럿이 어디에도 보이지 않던 해석에서 나왔다 — 드러나 있으면 사람이 한 번에 바로잡는다.
- 결함 이슈는 보고자가 본 상태(화면·데이터·로그)를 먼저 재현한다. 이슈에 적힌 "원인" 은 가설이다 — 재현으로 확인한 것만 계획의 전제로 쓴다.

끝나면 `issue-set.mjs --stage plan`. 무인: 묻지 않고 권장안을 택하되 전부 `--assume` 으로 남긴다.

## plan

계획은 드라이버가 직접 세운다. 이슈 원문·결정·읽은 코드가 곧 재료이고, 다른 에이전트에게 넘기면 그 재료가 요약으로 줄어든다. 목적은 문서가 아니라 **구현 전에 틀린 방향을 싸게 잡는 것**이다 — 작은 이슈는 가이드가 열 줄이어도 된다. 줄이는 것은 분량이지 아래 순서가 아니다.

조사할 곳이 넓으면(여러 표면의 전수 조사 · 묶음 이슈 · 처음 보는 영역) 조사를 `spawn_agent` 여러 개에 나눠 동시에 읽게 하고, 근거(`파일:심볼`)가 달린 요약만 받는다 — 드라이버가 차례로 다 읽으면 벽시계가 길어지고, 읽은 것이 전부 드라이버 컨텍스트에 남아 그 뒤 모든 호출이 비싸진다. 가이드 초안과 사이드카는 그 요약으로 드라이버가 쓰고, 4번(기계 점검)부터 똑같이 간다.

1. **영향 범위를 훑는다.** 바꿀 코드의 진입점과 호출처, `wiki.index` 에서 키·핵심어로 찾은 문서, 프로젝트 지침·메모리가 이 영역에 대해 말하는 함정을 읽은 뒤 아래 자리를 하나씩 코드로 확인한다 — 계획에서 빠졌다가 리뷰·재작업에서 나온 것의 대부분이 여기였다. 걸리면 `touched`·DoD 에 넣고, 안 걸리면 가이드에 "해당 없음(이유)" 한 줄로 남긴다.
   - 같은 동작의 다른 진입점(다른 화면·API·배치·모바일·내보내기)과 공용 함수의 다른 호출처
   - 반대편 표면 — 서버를 바꾸면 클라이언트 계약, 화면을 바꾸면 서버 검증
   - 권한의 모든 층(메뉴·라우트·서버 가드·데이터 범위)과 그 층을 거치지 않는 쓰기 경로
   - 같은 값을 계산·표시하는 다른 곳(목록·상세·합계·문서·알림)
   - 모든 언어의 문구
   - 외부 호출·비동기·트랜잭션 뒤의 실패 경로(부분 성공·재시도·동시 실행)
   - 이 변경으로 틀려지는 문서·규칙·설정 예시
2. **가이드 초안** — `wiki.dev_guide` 의 `{KEY}` 를 채운 경로에 `.draft` 를 붙여 쓴다(다중 키도 첫 키로 한 장 — 서버·클라이언트를 두 장으로 쪼개지 않는다). 결정을 적는 문서다. 코드를 옮겨 적지 않고(옮겨 적은 개수·줄 번호가 계획 오류의 출처였다) 자리는 `파일:심볼` 로 가리킨다.
   - `## 요구` — `R1`, `R2` … 관측할 수 있는 문장(누가 무엇을 하면 무엇이 보인다·저장된다·거부된다)과 근거(이슈 키·결정).
   - `## 결정과 가정` — 뒤집으면 안 되는 결정, 그리고 가정마다 틀렸을 때 바뀌는 범위. 사람이 정하지 않았는데 계획이 고른 해석은 상태에도 남긴다 — `issue-set.mjs --assume "<갈림길>" "<고른 해석 — 근거>"`(승인 요약과 마감 보고의 맨 위에 오른다).
   - `## 범위 밖` — 하지 않는 것과, 그래서 사용자가 화면에서 계속 보게 되는 것.
   - `## 설계` — 무엇을 어디에 왜. 기존 패턴과의 관계, 건드리지 않는 것, 함정, 구현 순서, 마이그레이션·배포 순서. 원인을 모르는 결함이면 가설과 가설별 확인 방법.
   - `## DoD` — `D1 (R1, R2) 확인할 것` 한 줄씩. 명령은 사이드카에만 둔다(두 곳에 적으면 어긋난다).
   - `## 리스크` — 되돌리기 비싼 것과 완화책.
3. **사이드카** `<runtime>/issues/<slug>.plan.json` = `{guides, touched, dod, lanes?}`.
   - `guides` `{KEY: 확정 경로(.draft 를 뺀 이름)}` · `touched` 손댈 파일(근사치다 — 구현 중 늘면 `issue-set.mjs --touched <경로>`).
   - `dod` `[{id, text, tests | probe, cwd?, expect?, human?}]` — 고르는 기준은 **틀린 구현이 초록으로 지나가지 못하는가**다.
     - 요구(R)마다 하나 이상. "막는다" 는 막히는 사례로, "보인다" 는 경계값과 반대 사례로 잰다 — 통과 사례뿐인 DoD 는 검사 0건과 구분되지 않는다.
     - 결함 수정의 첫 DoD 는 보고된 상태를 재현하는 테스트다(고치기 전에 빨강인 것을 본다).
     - 기대값은 구현과 독립된 리터럴로 적는다.
     - 쿼리·외부 전송·권한 가드·직렬화는 mock 을 거치지 않는 실제 경로를 한 번은 태운다(mock 은 쿼리를 실행하지 않는다).
     - 가드·검사를 새로 만들면 위반 주입 프로브 하나 — 일부러 어긴 상태에서 FAIL 하는가. 원복은 사본으로 하고(cp → 주입 → 실행 → mv. `git checkout --`·`stash` 는 커밋 전 수정까지 지운다) 주입할 토큰이 소스에 없으면 비0 으로 끝낸다.
     - 테스트를 도는 항목은 `tests: {stack, select[]}` + `expect.min_tests`(그 스택에 `dod_tests` 설정이 있을 때 — 게이트가 스택별로 한 번에 돌려 항목마다 판정한다). `select` 는 실제 테스트 이름·경로와 글자까지 같게 쓴다(gradle-junit 은 클래스 패턴 `*FeeCalculatorTest*`, vitest 는 스택 dir 기준 경로). `min_tests` 는 0건 실행이 초록이 되는 것을 막는 하한이다 — 그 요구를 재는 테스트 수를 넣되 닿을 수 없는 값은 쓰지 않는다. 그 밖의 확인은 `probe`(셸 한 줄) + `expect.pattern` 이고, 건수를 찍지 않는 프로브에는 `min_tests` 를 넣지 않는다(상시 FAIL 이 된다).
     - 화면이 바뀌면 `human: true` 항목을 두고 구현 뒤 실제 화면에서 확인한다(§implement). probe·tests·human 이 모두 없는 항목은 쓰지 않는다.
     - 하위이슈가 붙었으면 하위마다 DoD 가 하나 이상이고 text 가 `[KEY]` 로 시작한다(한 항목이 여러 하위를 덮으면 `[ABC-12·13]`). 이번에 구현하지 않는 하위도 human 항목으로 남겨 마감 때 미확인으로 보이게 한다.
     - 기존 전체 테스트(회귀)는 DoD 로 다시 적지 않는다 — 게이트와 main 배치가 돈다.
   - `lanes` — **이슈 1건이면 적지 않는다**(드라이버가 직접 구현한다). **이슈 여러 건(키가 둘 이상 · 하위이슈가 붙었다)이면 이슈마다 레인 하나**를 적는다 — §implement 가 그 레인들을 동시에 돌린다: `[{name, key, model, files, worktree, brief, dod}]`. `name` 은 키를 소문자로 줄인 `abc-12` 꼴(영문 소문자로 시작하고 레인끼리 서로 다르게 — 결과 파일·작업트리 브랜치·pane 이름이 된다), `key` 는 그 레인이 맡은 이슈 키다(고칠 코드가 없는 부모 키에는 레인을 만들지 않는다).
     - `dod` 는 그 레인이 통과시켜야 하는 DoD 의 id 배열(`["D1", "D3"]`)이다 — 레인은 구현 중 이 항목들의 테스트만 한 번에 묶어 돌린다(§implement). 합친 뒤에야 잴 수 있는 항목(여러 레인에 걸친 확인 · 사람 확인)은 어느 레인에도 넣지 않는다.
     - 같은 파일을 고치는 이슈들은 한 레인에 합치고(`brief` 에 함께 맡은 키를 적는다), 레인이 4개를 넘으면 가까운 이슈끼리 묶는다 — 동시에 도는 빌드·테스트는 서로를 느리게 한다. 가이드 `## 설계` 에 「레인 ↔ 이슈」 대응을 레인마다 한 줄씩 적는다.
     - `brief` 에는 가이드 요약이 아니라 그 레인만의 것(소유 경계 · 누가 부르고 누가 받는지 · 멈추고 보고할 조건)을 적는다.
     - `lane_runner`(`issue-start.mjs --status` 출력)가 `herdr` 면(§implement ①) `kind`·`kind_reason` 도 고른다(`herdr.kinds.implement` 풀 · 성향표 `herdr.kinds.profiles`). `workflow` 면 `worktree` 는 전부 false 다 — 레인들이 한 작업트리에서 동시에 돌므로 파일 소유가 한 파일도 겹치면 안 된다(이 세션에는 레인 작업트리의 변경을 가져올 단계가 없다 — true 로 적으면 점검이 `LANE_WORKTREE` 로 알린다).
     - 다른 이슈가 기대는 선행 작업(DDL·공통 계약)은 레인이 아니라 Phase 0 이다 — 메인이 먼저 구현·커밋한다.
     - 이슈 1건을 사용자가 병렬로 구현하라고 명시했을 때도 같은 모양으로 적는다(`key` 없이).
4. **기계 점검과 반영** — `issue-set.mjs --merge <사이드카> --from plan`. 반영하기 전에 스크립트가 글자 대조로 끝나는 것을 본다: 요구↔DoD 대응 · 가이드와 사이드카의 DoD 어긋남 · 확인 방법 없는 항목 · `select` 0건 매치 · 건수 하한 없는 러너 프로브 · 원복이 위험한 주입 프로브 · 레인 이름(겹침 · 파일 이름으로 못 쓰는 글자) · 레인 파일 겹침 · 이 세션이 돌릴 수 없는 작업트리 레인 · 레인이 가리키는 DoD id · 하위이슈 DoD · 빈 `touched`. **오류가 있으면 아무것도 반영하지 않고** 줄마다 고칠 곳을 낸다 — 고쳐서 다시 부른다. 경고는 반영되지만 읽고 판단한다(이슈 여러 건인데 레인이 없다는 `LANES_SERIAL` 은 「차례로 구현된다」는 뜻이다 — 레인을 적거나, 차례로 할 이유를 승인 요약에 올린다). 규칙을 알려고 스크립트 소스를 읽지 않는다 — 틀린 곳은 출력이 줄마다 알려 준다. 반영 없이 미리 보려면 `plan-check.mjs --json`.
   점검을 건너뛰는 길은 `--no-check "<사유>"` 하나다(사유가 history 에 남는다) — 이전 버전에서 승인받은 계획을 다시 반영할 때처럼 표기만 다른 경우에 쓰고, 보통은 가이드 DoD 줄에 `(R#)` 를 적어 넣는 편이 빠르다.
5. **반증 한 번** — 계획을 세운 컨텍스트는 자기 계획의 빈틈을 잘 못 본다. 새 컨텍스트 에이전트 하나가 이슈 원문·결정·가이드·사이드카와 코드를 읽고 "이대로 구현하면 틀리게 되는 곳"(요구 누락·오독 · 영향 범위 누락 · 틀린 구현도 통과하는 DoD · 결정과의 모순)을 찾는다.
   `spawn_agent` 로 에이전트 하나를 띄우고 프롬프트에 넣는다: 프로젝트 루트 절대 경로 · 이슈 원문(키마다 전문) · 결정과 가정(상태 JSON `decisions` — `assumed` 인 것은 `[가정]` 으로 표시) · 가이드 초안과 사이드카의 절대 경로(직접 읽게 한다) · 4번의 경고 줄 · 규율(읽기 전용 · 더 나은 설계 제안이 아니라 틀리게 되는 곳만 · 코드나 원문에서 확인한 것만 blocker 로, 확인하지 못한 의심은 notes 로 · 최대 25턴). 반환은 JSON 한 덩어리 `{verdict: PASS|BLOCK, blockers[{what, why, where}], notes[], looked[]}` 이고 `looked` 는 실제로 열어 본 파일과 대조한 원문 문장이다. 에이전트가 죽었거나 `looked` 가 빈 PASS 는 통과가 아니다(검사 0건) — 다시 띄우거나, 건너뛴 사실을 승인 요약에 적는다.
   - blocker 는 `where` 를 열어 직접 확인한다. 맞으면 가이드·사이드카를 고쳐 4번을 다시 하고(사람 결정이 필요한 것은 grill 로 돌아가 묻는다), 틀리면 기각 사유 한 줄을 남긴다.
   - 고쳤으면 **한 번만** 더 돌린다(반증은 최대 2회). 그래도 남는 것은 그대로 승인 요약에 올린다 — 통과시키려고 요구를 범위 밖으로 옮기거나 DoD 를 깎지 않는다.
   - 바꾸는 곳이 한 군데이고 요구가 한 문장으로 닫히는 이슈는 건너뛸 수 있다 — 건너뛰었다고 승인 요약에 적는다.
6. **승인** — 가정(있으면 맨 위) · 요구 · 범위 밖 · DoD(자동 n건 · 사람 확인 n건) · 레인 구성(이슈 여러 건일 때 — 「이슈 n건 → 레인 m개」와 묶은 이유. 차례로 하기로 했으면 그 이유) · 되돌리기 비싼 결정 · 반증 결과(통과 / 고친 것 / 남은 것·기각한 것 / 건너뜀)를 5~10줄로 보이고 request_user_input(진행(권장) / 수정할 것 있음 / 다시 계획). go/no-go 가 아니라 수정 요청을 받는 자리다. 묻기 직전에 `node "<P>/scripts/herdr-report.mjs" --notify "<KEY> 계획 승인 대기" --sound request`(Herdr 밖이면 무동작 — 사람 확인 DoD 로 멈출 때도 같은 한 줄, 제목만 `<KEY> 사람 확인 DoD <id>`).
   승인되면 ① `.draft` 를 확정 파일명으로 옮긴다 ② `wiki-row.mjs --index <wiki.index> --key <KEY> --set "<상태열>=planned" --set "<가이드열>=<경로>" … --log <wiki.log> --event "<한 줄>" --phase forecast`(열 이름은 `wiki.schema` 문서의 표 정의를 따른다 — 하드코딩하지 않는다) ③ `issue-set.mjs --stage implement --note approved`.
   무인: 진행(권장) 으로 간주하고 note 는 `approved(unattended)`.

## implement

- **이슈 1건은 드라이버가 직접 구현한다.** 가이드의 DoD 가 작업 목록이다. 이슈 1건을 여러 에이전트에게 나누면 띄우기·경계 맞추기·결과 회수가 붙고, 그 비용이 병렬 이득보다 컸다 — 사용자가 이 이슈의 병렬 구현을 명시했을 때만 아래 레인 경로를 쓴다.
- **이슈 여러 건(키가 둘 이상 · 하위이슈가 붙었다)은 이슈마다 레인 하나로 동시에 구현한다 — 병렬의 단위는 이슈다.** 상태 JSON `lanes` 가 그 구성이다(plan 이 레인마다 `key` 를 적었다). 드라이버는 Phase 0(다른 이슈가 기대는 DDL·공통 계약 — DTO·API 경로·이벤트 이름)을 먼저 구현·커밋하고, 레인을 **한꺼번에** 띄우고, 돌아온 결과를 합쳐 레인 경계(seam — 한쪽이 부르고 다른 쪽이 받는 곳)를 직접 대조한다. 레인이 1개뿐이면(전부 한 레인으로 묶였다) 띄우지 않고 직접 구현한다. 레인을 돌리는 수단은 환경이 정한다.
  - ① **Herdr 구현 레인** — `lane_runner` 가 `herdr` 일 때(이 세션이 Herdr 안이고 `herdr.lanes` 가 `implement`/`all`). `node "<P>/scripts/herdr-lanes.mjs" implement --slug <slug> [--lanes a,b] [--contracts-file <Phase 0 계약 md>] [--dry-run] --cwd <일하는 트리> --json` — 레인마다 `lane/<slug>/<name>` 작업트리와 `kind` 에이전트 pane 을 띄우고, 끝나면 diff 를 패치로 회수해 일하는 트리에 적용한다(`applied: yes|conflict|skipped|empty|no-apply` — `conflict` 는 메인이 표식을 푼다). Phase 0 은 먼저 커밋한다 — 작업트리는 HEAD 에서 갈리므로 커밋 안 된 수정은 레인이 못 본다(출력 `dirty_base`). 결과는 실행기가 `lanes[].kind·result` 에 남긴다(`--merge` 불필요).
    레인은 자기 작업트리에서 **자기 DoD 테스트만** 한 번에 돌린다 — 실행기가 레인 지시문에 `gate.mjs --try --slug <slug> --lane <name>` 을 넣어 준다(아래 「구현 중 테스트」). 전체 테스트·전체 lint·build·위반 주입은 레인이 돌리지 않는다.
    실행기는 **레인의 결과 파일이 생길 때까지** 기다린다(상한 `herdr.lane_timeout_s` — 구현 레인은 3600초보다 짧게 잡지 않는다) — 긴 테스트를 돌려 두고 쉬는 레인은 끝난 것이 아니다. 실행기가 먼저 끝났거나 죽었으면 레인을 다시 띄우지 말고 `implement --harvest` 로 끝난 레인의 결과만 회수한다. 절차·함정은 [herdr-lanes.md](herdr-lanes.md) §implement. `kind` 에는 codex 자신도 들어갈 수 있다. 출력이 `ok:false` 면(Herdr 밖 · 설정이 꺼져 있다) ② 로 간다.
  - ② **`spawn_agent` 레인** — `lane_runner` 가 `workflow` 일 때(그 밖의 모든 세션). `spawn_agent` 로 레인마다 서브에이전트를 **한꺼번에** 띄운다. 레인들은 한 작업트리에서 동시에 고친다 — plan 이 파일 소유가 겹치지 않게 나눴고(`worktree` 는 전부 false), 겹치는 이슈는 한 레인에 묶여 있다. **상태의 레인에 `worktree: true` 가 있으면 그대로 띄우지 않는다** — Herdr 안에서 세운 계획을 밖에서 잇는 경우이고, 그 계획은 레인끼리 파일이 겹치는 것을 허용했을 수 있다(여기에는 레인 작업트리의 변경을 가져올 단계가 없다). 계획 사이드카에서 그 레인들의 `worktree` 를 false 로 고쳐 plan 4번(`--merge … --from plan`)을 다시 하고, 점검이 `LANE_OVERLAP` 오류로 알리는 레인들은 한 레인으로 묶는다. 그 점검이 보는 것은 같은 패턴 문자열과 사이드카 `touched` 에 적힌 파일의 겹침뿐이다 — 구현 중 `--touched` 로 더한 파일은 사이드카 `touched` 에도 옮겨 적고, 레인끼리 같은 파일을 고치지 않는지는 레인의 `files` 를 직접 대조한다. 레인 프롬프트에 넣을 것: 가이드 경로(먼저 정독) · Phase 0 계약(바꾸지 말 것) · 그 레인의 담당 파일·`brief`·DoD · 규율(담당 파일 밖은 고치지 않고 경계에서 상대 레인의 파일을 고쳐야 하면 notes 에 적는다 · **빌드·테스트·lint 는 돌리지 않는다** — 같은 작업트리에서 다른 레인이 동시에 고치는 중이라 남이 반쯤 쓴 파일까지 컴파일된다. 테스트 코드는 쓰고, 드라이버가 돌려야 할 테스트(클래스·파일)를 notes 에 적는다 · 테스트를 돌리지 않은 것은 미완이 아니다 · 못 끝냈으면 숨기지 않는다) · 산출물로 사이드카 `<runtime>/issues/<slug>.lane-<name>.json` — `{"name", "status": "done|partial|failed", "files": […], "tests": {"command", "passed", "failed"}, "notes"}`. 끝나면 레인별 사이드카를 `issue-set.mjs --merge` 로 반영하고, 드라이버가 `gate.mjs --try` 한 번으로 DoD 테스트를 돌려 실패한 것만 고쳐 다시 돌린다. 완주는 사이드카 파일과 서브에이전트의 반환 둘 다로 판정한다.
- **하위이슈가 붙은 브랜치**(상태 JSON `subtasks` 가 있다): 코드는 한 브랜치·한 상태 JSON 에 쌓이고, 레인 = 하위이슈 한 건이다(`name` = 키를 소문자로 줄인 `abc-12` · `key` = 이슈 키). 다른 하위가 기대는 선행 하위는 Phase 0 로 메인이 먼저 한다. 게이트·리뷰는 브랜치 전체에 한 번이다.
- 레인의 완주는 반환값으로 판정한다 — 산출물 파일이 있다고 완주가 아니다(중간에 죽은 레인도 파일은 남긴다). Herdr 레인은 `status` 가 `done` 이고 사이드카가 `failed` 가 아닐 때만 패치가 적용된다. `partial`·`failed` 레인의 남은 일은 드라이버가 합친 트리에서 이어 한다(같은 레인을 처음부터 다시 띄우지 않는다).
- **구현 중 테스트는 `node "<P>/scripts/gate.mjs" --try` 로 돌린다.** 게이트가 아니라 확인이다 — 상태·판정을 기록하지 않고(로그 파일만 남는다) push 전 게이트를 대신하지도 않는다. DoD tests 항목을 스택마다 **한 번에** 묶어, push 전 게이트가 DoD 를 재는 것과 같은 명령·환경 파일·판정으로 돌리므로, 러너 명령을 손으로 조립해 한 건씩 띄우지 않는다(기동·컴파일을 건수만큼 치른다).
  - 전부 `--try` · 일부 `--try --ids D1,D3` · 고친 파일을 덮는 기존 테스트는 `--try --stack <스택> --select '<패턴>' [--select …]`. 실패하면 고친 뒤 출력의 「다시」 줄에 나온 명령으로 **실패한 것만** 다시 돌린다(「다시」는 항목의 통과 건수 하한을 재지 않는다 — 하한까지 다시 보려면 「항목판정」 줄의 명령). 스택에 `dod_tests` 설정이 없으면 `--try` 가 묶어 돌릴 수 없다 — 그 스택의 러너를 직접 부르되 원칙은 같다(자기 테스트만 · 한 번에 묶어서).
  - 구현 단계에서 돌리지 않는 것: 전체 테스트 · build(main 배치가 돈다) · 전체 lint(커밋 게이트가 돈다) · 위반 주입 프로브의 반복 실행. 프로브는 처음 만들었을 때 `--try --ids <id>` 로 발화를 한 번 확인하면 된다 — 그 뒤는 push 전 게이트가 돈다.
  - 띄운 명령은 끝날 때까지 기다린다(같은 테스트를 또 띄우면 두 벌이 겹쳐 둘 다 느려지고, 한 작업트리에서는 러너의 리포트 폴더까지 겹친다). `--try` 가 초록이면 구현 단계의 테스트 확인은 끝이다 — 같은 테스트를 게이트 직전에 손으로 한 번 더 돌리지 않는다(push 전 게이트가 그 확인이다).
- 결함은 재현 테스트가 빨강인 것을 먼저 보고 고친다.
- 구현 중 계획과 달라지면 가이드와 상태를 같이 고친다 — 새로 걸리는 파일은 `--touched`, 새로 고른 해석은 `--assume`, 바뀐 검사는 사이드카를 고쳐 4번(`--merge … --from plan`)을 다시(검사가 그대로인 항목의 판정·근거와 구현 중 더한 기록은 남고, 검사가 바뀐 항목만 다시 잰다). 승인받은 검사를 조용히 바꾸지 않고 보고에 남긴다. 요구의 뜻이 달라지는 발견이면 멈추고 묻는다.
- 끝내기 전에 ① 바뀐 영역의 기존 테스트를 실제로 돌린다(`--try --stack … --select …` 로 한 번에) — 깨질 테스트를 계획에서 미리 다 찾지는 못한다 ② 화면이 바뀌었으면 실제 화면에서 확인하고 `issue-set.mjs --dod-result <id> PASS --evidence "<어디서 무엇을 봤는지>"` 로 남긴다. 사람 확인 항목은 근거 없이는 PASS 가 되지 않는다 — 볼 수단이 없으면 그대로 두고 보고에 "사람 확인 필요" 로 남긴다.
- 구현 중간 커밋은 gate → commit 순서 그대로.
